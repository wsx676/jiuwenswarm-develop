## 二、核心思路

### 2.1 问题建模：四层架构

赛题拆成四个层次，这是全文的骨架：

| 层次 | 职责 | 关键模块 |
| --- | --- | --- |
| **数据获取层** | 实时数据爬取 + 标准化处理 | 股票行情、财务三大表、新闻资讯、宏观指标 |
| **分析计算层** | 财务/技术/宏观分析 | ROE 分解、财务比率、现金流分析、同业对比 |
| **内容生成层** | 结构化 + 多模态生成 | 文本生成、图表生成、表格展示、图文一致性 |
| **质量控制层** | 内容验证 + 格式规范 | 数据准确性、逻辑一致性、引用来源验证 |

并进一步指出可以加循环（审核发现问题→再生成）和数据质量审查（分析时判断数据是否足够→不够继续采集）。

### 2.2 数据采集方案

 用三条腿走路，全部免费公开渠道：

- **akshare**：获取财务三大表（资产负债表/利润表/现金流量表）、股权结构、公司基础信息
- **duckduckgo-search (DDGS)**：搜索行业地位、市场份额、竞争分析等非结构化信息
- **自写爬虫**：东方财富港股财务报表、同花顺主营介绍与股东信息

> **结合当前比赛的优化**：当前比赛面向 A 股沪深上市公司（见上表六大板块），akshare 对 A 股支持更完善（无需港股爬虫适配）。建议按板块批量采集：以板块为单位，一次性拉取该板块所有公司的三大表与行情数据，既提升效率，又天然形成同业对比数据集。注意：报告需标注数据来源以保证可复现性。

### 2.3 数据分析 Agent（核心）

这是最核心、最有参考价值的部分。它没有用现成多 Agent 框架，而是自建了一个**基于 Notebook 环境的代码执行智能体**：

**CodeExecutor（代码执行器）**：
- 基于 IPython InteractiveShell，模拟 Jupyter Notebook 的**持久化、有状态**执行环境——变量和上下文在不同代码块间传递
- **AST 静态分析 + 白名单机制**：只允许 `pandas/numpy/matplotlib/duckdb` 等安全库，禁止 `exec/eval` 等高风险内置函数
- 预导入常用库、配置中文字体（SimHei）、追踪新生变量、捕获 stdout/stderr、格式化 DataFrame

**DataAnalysisAgent（数据分析智能体）**：
- 采用 **ReAct 思路**（观察→推理→行动→循环），多轮对话驱动
- 三种动作（每次只做一个动作）：
  - `generate_code`：生成 Python 分析代码
  - `collect_figures`：收集已生成图片并分析解读
  - `analysis_complete`：生成最终分析报告
- **YAML 格式输出**：思考过程和行动建议严格用 YAML 包裹，便于程序解析执行

**上下文管理技巧**（解决"报表太大导致上下文爆炸"）：
- 表格只给模型看**表头 + 前 5 行 + 后 5 行**，不全量打印
- 多种记忆分离管理：图片收集、分析结果收集、对话历史交互记录，不同环节用不同记忆

### 2.4 两阶段研报生成流程

**阶段一：数据采集与基础分析**
1. AI 识别竞争对手 → 获取目标公司及竞对的财务报表（CSV）
   > **结合当前比赛优化**：当前比赛已提供六大板块分类（见一补节），同板块公司天然为竞对，可直接按板块批量提取竞对名单，省去 LLM 猜测环节。例如分析宁德时代时，新能源/电力板块的比亚迪、阳光电源等自动成为竞对。
2. 获取公司简介（TXT）→ DuckDuckGo 搜索行业信息（JSON）
3. DataAnalysisAgent 执行三类分析：
   - 单公司财务分析
   - 两两对比分析（目标公司 vs 每个竞对）
   - 特定公司估值与预测分析（DCF、敏感性测试）
4. 汇总保存为 Markdown

**阶段二：深度研报生成（分治策略）**
1. 图片本地化：网络图片下载到本地 `images/`，统一相对路径
2. **先让 LLM 生成 YAML 格式大纲**（part_title + part_desc）
3. **再分段逐章生成**：遍历大纲，每段传入"前文 + 背景 + 原始材料"，严格图片引用规则（只允许引用真实存在的本地图片）
4. mdformat 格式化 + pandoc 转 DOCX
   > **结合当前比赛**：当前比赛交付为 Markdown（`股票代码.md`），DOCX 转换可省略。

### 2.5 Baseline 的技术栈与得分

| 项 | 值 |
| --- | --- |
| 模型 | DeepSeek V3（开源，160k 上下文，16k 输出） |
| 框架 | pocketflow（轻量工作流引擎）+ 自建 Agent ⚠️ 当前比赛要求替换为 JiuwenSwarm 框架 |
| 耗时 | 2-4 小时 / CPU 环境 |
| 得分 | 公司研报 4.75/10，行业/宏观为 None |

### 2.6 Baseline 自述的缺陷

教程坦率承认了 baseline 的不足，这些正是进阶要解决的：
- 工作流 + 单 Agent，**泛化性差**
- **记忆爆炸**导致报错
- **格式化输出不稳定**，每次生成的研究报告不一致
- 数据分析 Agent 发挥不稳定，两次分析差异很大
- 定位仅为"研报生成"，而当前比赛要求 Agent 完成**选股决策 + 仓位配置**，需增设投资决策环节
- 采用 pocketflow + 自建 Agent，而当前比赛要求**深度耦合 JiuwenSwarm 框架**，需将其能力迁移为 JiuwenSwarm 的技能/多智能体团队/Swarmflow 工作流

## 三、进阶.md 核心思路

进阶文档针对 baseline 的短板，从四个维度给出优化方向：

### 3.1 记忆管理优化：混合记忆系统

模仿人脑，三层记忆协同：

| 记忆层 | 实现 | 作用 |
| --- | --- | --- |
| **短期记忆** | LLM 上下文窗口 | 当前对话和任务信息，容量有限易丢失 |
| **长期记忆** | 持久化存储 | 核心知识、历史经验、重要结论（经摘要/实体提取后存储） |
| **外部记忆** | 向量数据库 / 搜索引擎 | 知识库，语义相似度检索或关键词搜索 |

**混合机制**：实时判断哪些信息临时（入短期）、哪些有长期价值（摘要后入长期）；需要时短期 + 长期同时输入（长期以摘要形态较短），是否启用外部记忆由模型自行决定。

**关键洞察**：完成任务后，将结论和关键信息**总结**存入长期记忆，形成"增强上下文（Augmented Context）"再喂给 LLM。

### 3.2 数据收集优化：从"搜索"到"深度研究"

把简单关键词搜索升级为**迭代式查询与信息饱和**：

1. **初始查询**：根据目标生成几个核心搜索查询
2. **结果分析**：提取关键实体、概念和**新问题**
3. **查询精炼与扩展**：基于新信息生成更具体深入的查询（如发现"XX 新兴业务"→立即搜"XX 业务市场份额""主要竞争对手"）
4. **循环与终止**：重复直到不再返回有价值新信息（"信息饱和"）或达到搜索深度/次数限制

### 3.3 内容生成优化：迭代式精炼 + 多任务协同

**思路一：迭代式精炼**
- 草稿生成 → 自我批判（逻辑/数据/语言/矛盾）→ 迭代修改，直到达标

**思路二：多任务协同生成**
- 图表生成 Agent 读分析数据 → 调 matplotlib/ECharts 生成图片
- 主报告 Agent 撰写时引用已生成图表并围绕图表解读

### 3.4 RAG 优化（进阶方法 1）

**分块策略**：
- **混合分块（Hybrid Chunking）**：大"父块"保语义完整 → 细分"子块"精确检索 → 命中子块后返回完整父块
- **智能体分块（Agentic Chunking）**：分块智能体理解语义/逻辑/实体，自主决定切分点（完整逻辑单元结束才切）

**检索策略**：
- **混合检索（Hybrid Search）**：向量检索（语义相似）+ BM25（关键词精确）并行
- **结果重排（Re-ranking）**：合并两路结果后用重排模型精细化排序，取最相关优质结果

### 3.5 多智能体系统（进阶方法 2）

设计专业 Agent 团队，由"总监"协调：

| Agent | 职责 |
| --- | --- |
| 数据搜集官 | 执行 DeepSearch，收集原始数据 |
| 财务分析师 | 解析财报、计算财务比率、杜邦分析 |
| 行业研究员 | 行业趋势、竞争格局 |
| 图表绘制师 | 数据转图表 |
| 报告撰写师 | 整合分析结果和图表成流畅报告 |
| 项目总监 | 理解需求、拆解任务、分配监督 |

### 3.6 数据分析要点

进阶文档强调让 Agent 充当"初级分析师"：
- **财务比率计算**：杜邦 ROE 分解、现金流匹配度
- **数据关联与对比**：与行业均值、竞对横向对比
- **模型构建与预测**：DCF 估值，设合理假设（增长率/折现率），做敏感性分析
- **图表生成**：市场份额变化、财务指标趋势可视化

## 四、两篇文章中值得参考的思路

下面逐条分析两份资料中**真正有参考价值、可直接借鉴**的设计点。

### 4.1 来自 Baseline 教程的可参考点

**① Notebook 式代码执行器（强烈推荐）**

这是 baseline 最有工程价值的设计。用 IPython shell 构建持久化、有状态的执行环境，让 LLM 生成的代码在受控沙箱里跑，变量跨代码块保留。相比"写文件再运行"，它：
- 避免反复读写文件的繁琐
- 保留中间变量状态，适合多步数据分析
- AST 白名单 + 禁用 exec/eval 控制安全风险

> 参考价值：任何需要"让模型动态执行代码"的场景（数据分析、图表生成、财务计算）都可直接套用这套 CodeExecutor 设计。

**② 表格"头尾各 5 行"的上下文压缩技巧**

财务报表动辄上百行，全量打印必爆上下文。baseline 给模型看表头 + 前 5 行 + 后 5 行，既让模型理解结构又不撑爆窗口。

> 参考价值：处理大表格/长文档时的通用上下文压缩范式，简单有效。

**③ 分治式长报告生成（先大纲后分段）**

不让 LLM 一口气写完长报告（质量难控），而是：先生成 YAML 大纲 → 逐段生成（每段传入前文上下文）→ 严格图片引用规则。用"已生成内容反复喂回"突破单次输出长度限制。

> 参考价值：生成任何长篇结构化内容（研报、方案、文档）时的通用范式。

**④ 图片本地化与路径统一**

网络图片下载到本地、统一相对路径、移除失效引用——这是 Markdown 转 DOCX 前的必要预处理，保证可移植性。

> 参考价值：Markdown 报告中统一引用本地图片、移除失效链接，保证报告自包含。当前比赛交付为 Markdown 且要求**成果可复现**，图片本地化可保证第三方复现时图文完整。

**⑤ 三动作机制（generate_code / collect_figures / analysis_complete）**

用 YAML 约束 Agent 每次只做一个动作，把复杂流程拆成可控的小步骤，避免模型"一步到位"时的混乱。

> 参考价值：任何需要多步执行、且每步产出类型不同的 Agent 都可借鉴这种"单动作 + YAML 路由"模式。

**⑥ 竞争对手自动识别 + 两两对比分析**

先用 LLM 识别竞对，再对目标公司与每个竞对做两两对比，最后合并——形成了横向竞争分析的自动化闭环。

> 参考价值：行业/公司研报中"竞争格局"章节的自动化生成范式。
>
> **结合当前比赛的优化**：当前比赛已提供六大板块分类，同板块公司天然为竞对（如消费板块的贵州茅台 vs 五粮液 vs 山西汾酒），可直接从板块列表提取竞对名单，省去 LLM 识别环节，准确率更高。研报以 `股票代码.md` 命名批量产出，每家公司各自生成一份，板块内公司互为竞对做横向对比。

### 4.2 来自进阶.md 的可参考点

**① 迭代式查询与信息饱和（Deep Research 思路）**

从"搜一次"升级为"搜→分析→精炼→再搜"的循环，直到信息饱和。这是解决 baseline"数据不够深"的关键。

> 参考价值：当前比赛初赛看收益率与风控、决赛看报告完整性与逻辑严谨性，数据是决策与报告的基础，迭代式研究能显著提升数据的深度与广度。

**② 混合记忆系统（三层 + 混合机制）**

短期/长期/外部分层 + 实时判断分流 + 总结沉淀。baseline 的"记忆爆炸"问题正是缺乏这套机制。

> 参考价值：直接对应 baseline 自述的"记忆爆炸报错"缺陷，是必做的优化项。

**③ 迭代式精炼（草稿→批判→修改循环）**

引入"批判者"Agent 评估草稿（逻辑/数据/语言/矛盾），反馈给"作者"迭代修改，直到达标。

> 参考价值：当前比赛决赛重点考察投资报告的**完整性、逻辑严谨性**，用批判循环兜底报告质量、直接对应决赛评分维度。

**④ 混合分块 + 混合检索 + 重排**

RAG 三件套：父块保语义/子块精检索、向量+BM25 并行、Re-ranker 精排。解决"固定分块割裂语义""单向量检索漏关键词"问题。

> 参考价值：用公告、新闻、研报等文本构建外部知识库，配合混合检索提升报告事实依据质量，是减少幻觉的标准配置。

**⑤ 多智能体分工（六角色团队）**

把研报生成拆成数据搜集/财务分析/行业研究/图表绘制/报告撰写/项目总监六个专业角色，由总监协调。

> 参考价值：当前比赛强制深度耦合 JiuwenSwarm 框架，正好可将这六个角色落地为 JiuwenSwarm 多智能体团队中的专业 Agent（由总监角色协调），同时满足"框架强制性"与"多 Agent 协同"要求。

**⑥ "高质量入，高质量出"的数据源理念**

进阶反复强调数据源质量是研报质量的根本，没有好数据源一切优化都是空中楼阁。

> 参考价值：朴素但关键，提醒优化时先夯实数据采集，再谈分析和生成。

### 5.2 融合建议：取长补短的实践路线

两份资料恰好互补——baseline 提供"能跑通"的工程骨架，进阶提供"跑得好"的优化血肉。建议按以下路线融合：

**第一步：保留 baseline 的工程骨架（并迁移到 JiuwenSwarm 框架）**
- 四层架构（数据/分析/生成/质控）作为整体骨架
- CodeExecutor（Notebook 式代码执行器）作为分析计算层核心
- 先大纲后分段的分治式长报告生成
- 输出链路：图片本地化 + Markdown 最终产出按 `股票代码.md` 命名（pandoc 转 DOCX 可选，根据提交要求）
- 以六大板块为单位批量生成研报，同板块公司互为竞对做横向对比
- **框架落地（当前比赛强制要求）**：不得用未经封装的独立脚本绕过框架——CodeExecutor、数据采集、报告生成等能力均须封装为 JiuwenSwarm 的技能（SKILL.md + Python 模块）、多智能体团队或 Swarmflow 工作流

**第二步：用进阶思路替换/增强关键环节**

| baseline 环节 | 进阶增强 | 效果 |
| --- | --- | --- |
| 单次 DDGS 搜索 | 迭代式 Deep Research 至信息饱和 | 数据深度↑ |
| 表格压缩（被动） | 三层混合记忆 + 总结沉淀 | 记忆爆炸↓ |
| 单 Agent 工作流 | 六角色多 Agent 团队（落地为 JiuwenSwarm 团队） | 协同能力↑、泛化↑ |
| 线性分段生成 | 草稿→批判→修改迭代精炼 | 质量一致性↑ |
| 无 RAG | 混合分块 + 混合检索 + 重排 | 专业知识↑、幻觉↓ |
| 输出端图片约束 | 过程端批判 Agent 自检 | 质控覆盖面↑ |

**第三步：补齐当前赛题特有的投资决策环节（两份资料均未覆盖）**
- 增设**投资决策 Agent**：基于各公司研报结论输出选股名单与仓位权重（`Portfolio.json`），支持满仓/半仓/空仓
- 空仓决策须在报告中阐明决策逻辑（赛题明确要求）
- 分析维度对齐赛题：技术分析、基本面分析、宏观经济分析、另类数据挖掘、情绪因子构建
- 初赛只看收益率与风险控制指标——仓位决策环节直接决定晋级，优先级不低于报告生成
- 按"成果可复现性"要求：记录决策过程日志与资源消耗数据，附代码与环境说明

**第四步：分阶段落地，避免一步到位**
1. 先跑通 baseline（验证数据采集 + CodeExecutor + 分段生成链路）
2. 再加混合记忆（解决记忆爆炸，稳定运行）
3. 再加迭代式 Deep Research（提升数据深度）
4. 再加多 Agent 团队 + 投资决策环节（提升泛化、协同与仓位决策）
5. 最后加 RAG 三件套 + 批判循环（提升专业性和质量一致性）

### 5.3 特别注意的合规约束

以下约束以当前比赛 `要求.md` 为准（两份资料中涉及原 AFAC 赛题的约束已剔除）：
- **框架强制性（最重要）**：必须深度耦合 JiuwenSwarm（openJiuwen）核心能力模块，不得使用未经封装的独立脚本绕过框架约束——baseline 的 pocketflow 与自建 Agent 需全部迁移为 JiuwenSwarm 技能/多智能体团队/Swarmflow
- **投资标的限定**：严格限定于组委会公布的上市公司列表（六大板块，见一·补节），不得选择列表外标的；允许空仓，但须在报告中阐明决策逻辑
- **报告分析维度**：应包含充分分析过程，可综合运用技术分析、基本面分析、宏观经济分析、另类数据挖掘、情绪因子构建等方法论
- **评测标准**：初赛仅依据收益率及风险控制指标客观排名；决赛考察报告完整性、逻辑严谨性与答辩表现
- **可复现性**：提交材料须确保第三方可依据代码与环境说明完整复现投资决策过程及资源消耗数据
- **仓位自由度**：Agent 可自主决定满仓、半仓乃至完全空仓

## 六、总结

两篇文章构成了完整的"从 0 到 1 再到优"路径：

- **教程** 的最大贡献是 **CodeExecutor（Notebook 式代码执行器）** 和 **分治式长报告生成**——前者让模型安全地动态执行代码做数据分析，后者让长篇结构化报告可分段可控生成。这两点是可直接复用的工程骨架。
- **进阶.md** 的最大贡献是 **迭代式 Deep Research**、**混合记忆系统**、**多 Agent 团队** 和 **RAG 三件套**——这四点恰好精准对症 baseline 的"数据浅、记忆爆、泛化差、幻觉多"四大缺陷。

结合当前比赛（【华为openJiuwen】基于 JiuwenSwarm 的 Agent 金融分析报告生成）还需注意三点差异：
1. **任务升级**：从"生成研报"升级为"选股决策 + 仓位配置 + 报告"三位一体，两份资料均未覆盖仓位决策环节，需自行增设投资决策 Agent（输出 `Portfolio.json`，支持满仓/半仓/空仓）
2. **框架替换**：必须深度耦合 JiuwenSwarm 框架，baseline 的 pocketflow + 自建 Agent 需迁移为 JiuwenSwarm 的技能、多智能体团队与 Swarmflow 工作流，不得用独立脚本绕过框架
3. **目标转移**：初赛只看收益率与风险控制指标（投资表现），决赛才看报告质量——决策环节的优先级不低于报告生成；同时须满足成果可复现性（决策过程 + 资源消耗数据）

实践时建议以 baseline 工程骨架为底座，按"JiuwenSwarm 框架迁移→记忆→数据深度→多 Agent + 投资决策→RAG+批判"的顺序逐步注入优化，每步验证效果再推进，避免一次性重构带来的不稳定。

> 核心心法：**高质量入，高质量出**——数据源质量是决策与报告质量的根本，所有架构和 Agent 优化都建立在可靠数据采集之上。
